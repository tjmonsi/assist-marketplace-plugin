# Health

Report whether the assist-plugin hooks are working: the PreToolUse guards (`sa-mermaid-only`, `doc-cli-guard`, `commit-attribution-guard`, `pr-post-ask`, `pr-verdict-guard`, `prose-gate`, `fsa-write-bar`), the `injection-filter`, the `prose-advisor`, `writing-context`, the `confirmation-record` hook, and the `purpose-capture` hook, plus the `audit-log` hook. All of them fail open except four cases: a hook bug never blocks a command, write, or tool result; it lets the command or content through and records the failure. The exceptions are `pr-verdict-guard`, which fails closed for a command that looks like a PR verdict post (see its row below), the `Bash` route of `fsa-write-bar`, which fails closed for a subagent command that names a protected path (see the `fsa-write-bar` paragraph below), and `phi-outbound-guard` and `ferpa-disclosure-guard`, which fail closed for a `WebFetch` call or a `gh pr` or `bkt pr` post command (see their rows and paragraph below). The `injection-filter` replaces prompt-injection sentences in web, MCP, and subagent output with a visible marker; its self-test checks a fixed corpus of known injections (must be flagged) and benign text (must stay unchanged). The `prose-gate` denies writes to prose files that add block-tier writing-standard tells (em dashes, curly quotes, chatbot residue). The `prose-advisor` reports advisory tells after a write without blocking it. Both prose hooks skip files under the system temp directory and paths listed in `${CLAUDE_PLUGIN_DATA}/prose-gate-allowlist.json` (a JSON array of path substrings; the entry `"*"` disables the gate and the advisor for all paths; a malformed file means no allowlist). Files under `docs/tts/` are judged like other prose, with fenced blocks exempt. The allowlist is separate from `hooks-disabled.json`: a passing self-test never changes it, and the self-tests ignore it. The `commit-attribution-guard` denies a `git commit`, `git merge`, `gh pr create`, or `gh pr edit` command whose commit message or pull request body holds an AI attribution line: a Co-Authored-By trailer naming an AI tool or vendor (human co-authors pass, but a co-author named only Claude or Devin, or whose name contains a tool name, counts as the tool), a "Generated with/by" footer naming an AI tool, an Assisted-by or Generated-by trailer naming an AI tool, or a `*-Session:` trailer or bare session link at an AI host. Lines inside a closed code fence are skipped. It never rewrites the command, does not cover `git tag` or `gh pr merge --subject/--body` (the squash commit message), and cannot see a message built from a variable or piped through stdin; its self-test checks fixed deny and allow cases. The `pr-post-ask` guard asks the user before `gh pr review`, `merge`, `comment`, and `close`, `bkt pr approve`, `comment`, `decline`, `close`, and `merge`, and a `bkt api` call that may write (an option it does not recognize counts as a possible write), in every session. It asks and never denies, and it fails open. It is best-effort, and a bypass form found later is added to this list. Its known gaps, and no others: a program word taken from a variable or an expression (`G=gh; $G pr merge 1`, PowerShell `& (Get-Command gh) pr merge 1`), and PowerShell splatting; `gh api` with any method, `gh pr edit`, `gh pr ready`, `gh pr reopen`, a `gh` alias or extension that expands to a posting command, and `bkt pr` subcommands other than `approve`, `comment`, `decline`, `close`, and `merge`; a command string run by another program (`bash -c`, `sh -c`, `pwsh -Command`, `cmd /c`, `eval`, `Invoke-Expression`, `iex`, `Start-Process`, `xargs`, `find -exec`, `watch`, `npx -c`, `node -e`, a script file, a shell function, a coprocess), and argv wrappers outside the wrapper list (`setsid`, `doas`, `ionice`, `stdbuf --output 0 gh ...`); a posting command inside a command substitution in another program's argument (`echo $(gh pr merge 1)`), while a substitution in the program word or in an assignment value before it is judged and asks; a Bash program name in another case (`GH`), `.cmd`, `.bat`, and `.ps1` shims, shell aliases, and renamed or linked binaries; an option with a separate value ahead of the verb that the option lists do not name (`gh --body x pr comment 1`, `gh pr --body x comment 1`, `gh pr -b x comment 1`, `gh pr --body-file f review 1 --approve`, `bkt pr --text x comment 1`); a redirection the shared lexer splits into separate parts (`gh 2>&1 pr merge 1`, `gh >&2 pr merge 1`, `gh &>/dev/null pr merge 1`, `gh >| out pr merge 1`, `bkt 2>&1 pr approve 1`, `gh < <(true) pr merge 1`); a PowerShell array or script block in the verb position (`gh pr @('merge') 1`, `gh pr {merge} 1`), and a PowerShell comment that hides an opening parenthesis; the quoting forms `$"gh"` and `$'g\x68'`, brace expansion (`{gh,pr,merge,1}`), a glob in the program word (`/usr/bin/g[h]`), `(( x = 1 << 2 ))` read as a heredoc so the next line is hidden, and `sudo --user root gh ...` (the shared-parser forms `doc-cli-guard` lists); the PowerShell forms listed for `doc-cli-guard` (typographic quotes, block comments, the dot-source operator, typed, scoped, and compound assignments), and a redirection before the program (`2>/dev/null gh pr merge 1`); a REST request through `curl`, another HTTP client, or an MCP tool. It has no `bkt api` gap, because an unrecognized `bkt api` option asks. With several PreToolUse hooks, a deny from another hook beats this ask. The ask prompts in default and acceptEdits modes and forces a prompt in auto mode; in a non-interactive `-p` run with no one to answer, the call is denied. Unverified: whether the ask prompts in bypassPermissions mode or plan mode, and whether an installed mod can approve a call the hook would prompt for. The `pr-verdict-guard` denies `gh pr review` with any verdict flag (`--approve`, `--request-changes`, `--comment`) and `bkt pr approve` or `bkt pr decline` for a PR when `confirmations.jsonl` holds no recorded confirmation for that PR and verdict. It reads `confirmations.jsonl` only and never `pending.jsonl`, so a pending-action record alone does not satisfy it. It is additive: `pr-post-ask` is unchanged, a deny from the guard wins over that ask, and after a recorded confirmation the `pr-post-ask` prompt may still appear (two prompts). It does not cover `bkt pr comment`, a `bkt api` call, `gh pr merge`, `close`, or `comment`, or a SARIF upload, and it does not read a verdict post inside a command substitution or a command string run by another program. If the guard fails after its input was read (an error, or a timeout), it denies a command that looks like a PR verdict post and logs the failure; a failure before that point (an unsupported Node, a module that does not load, unreadable input) and a disabled guard let the command run with a warning. On an allow it appends the confirmation reference to `${CLAUDE_PLUGIN_DATA}/pr-verdict-log.jsonl` (newest 200 lines). Its self-test runs fixed cases against a stub store, so no real store is read or written. The `confirmation-record` hook runs on `UserPromptSubmit` and records the user's confirmation of a PR verdict post. It reads only the message the user typed, finds the per-action token in it, matches the token to an unused, unexpired pending-action record of the same session in `pending.jsonl`, and only then writes a record to `confirmations.jsonl` and marks the token used. An affirmative with no token, text in a quote line or code fence, an expired or reused token, and a token of another session write no record, and a failure to write leaves no record, so the posting guard has nothing to allow. It never blocks or changes the message. Its self-test runs a temporary project root with four fixed cases: one genuine confirmation that must record, and a forged-text case, an affirmative-without-token case, and an expired-token case that must not; a record for a case that must not record, or a missed genuine record, disables the hook, which then writes nothing. The `purpose-capture` hook runs on `UserPromptSubmit` and writes the session purpose record `.agent/governance/session-purpose.json` when the first non-blank line of your own message starts with `Purpose:` (for example `Purpose: review grading anomalies`; 1 to 200 characters on one line). The record holds the purpose, the writer `hook`, the session id, and a timestamp, never the rest of the prompt. A `Purpose:` line in a quote line, a code fence, pasted text below your first line, a tool result, or model output records nothing, and no tool can write the file. With no declaration the hook writes nothing and the FERPA and HIPAA access logs show the purpose as `unstated`; a missing purpose never denies an access. It never blocks or changes the message. Its self-test runs a temporary project root with six fixed cases: one declared purpose that must record, and five forged or undeclared cases that must not; a record for a case that must not record, or a missed declared purpose, disables the hook, which then writes nothing. `writing-context` adds the compact writing standard to the session and to each subagent; its self-test checks that the standard is readable. A failure is reported and never disables the hook, so a failed self-test leaves it enabled and it never appears under disabled guards. The `audit-log` hook runs on every `PostToolUse` event and appends one access record to the governance audit log, `.agent/logs/governance/audit.jsonl` under the project root. The log is a hash-chained JSONL file: each line holds the SHA-256 hash of the line before it, so a later reader can detect an edit, a deletion, or a reordering. After each deny or ask, a guard appends a decision record to the same log. A record holds the event, the decision and rule id (decision records), the tool name, a path with its data-class tag, and the agent identity. It never holds command text, prompt text, file contents, tool results, or secret values; the log library refuses a record that carries a secret-shaped value and writes nothing for it. Logging is always on and fails open: a failed or refused write is noted in `hook-health.jsonl`, the tool call proceeds, and a guard decision never changes. The log exists from the first session: at session start the health check creates `.agent/logs/governance/audit.jsonl` when it is absent, with no opt-in and no profile setting. At session start it also appends one `guard-disabled` event for each guard or filter listed in `hooks-disabled.json`, naming the guard (the line carries the time). A guard is logged once per project while it stays disabled, and a later session adds no duplicate; a guard that is re-enabled and later disabled again is logged again. A guard disabled in the middle of a session is logged when its first skipped call runs. The dedup record is `disabledAudited` in `${CLAUDE_PLUGIN_DATA}/health-state.json`, not an audit record. The event holds no disable reason, command, path, or secret, and logging it never changes whether the guard is disabled or what the notice prints. The `audit-log` self-test uses a stub sink, so it reads and writes no real log; it checks that each record carries the tool, the path with its tag, and the agent identity, and holds neither a secret string nor the command text. A failed self-test is reported and never disables the hook, because disabling it would stop the audit trail; the hook stays enabled and the log may be incomplete. The `phi-outbound-guard` (HIPAA profile) denies a `WebFetch` call or a `gh pr` or `bkt pr` post command whose payload matches a `phi_patterns` entry or names a PHI-tagged path. The `ferpa-disclosure-guard` (FERPA profile) judges the same calls: when the payload matches a `student_record_patterns` entry or names a student-record-tagged path, it requires a declared `Receiving-Party:` that is on the `ferpa_receiving_parties` allowlist in `.agent/governance/profile.json` and a `Legitimate-Interest:` label, records the disclosure in the audit log (the party identifier, the label, the path, and the class tag, never the content), and denies the call when either is missing, when the party is not listed, or when the event cannot be recorded. A party under a `ferpa_exceptions` entry (a 34 CFR 99.32(d) exception) needs no entry and the call proceeds. While HIPAA is enforced, the `phi-outbound-guard` also denies a `WebFetch` call (by URL host) or a `gh pr` or `bkt pr` post (by platform: github.com or bitbucket.org) to an external system that `profile.json` lists under `external_systems` but has no `baa_references` entry for; a host that no listed system names is not judged. The allowlist in the protected `profile.json`, not the payload text, decides which parties pass. **The FERPA disclosure control's status is to verify**: it is the only control cited against 34 CFR 99.32, its exception handling is not yet reviewed, and it is not full 34 CFR 99 compliance. Both guards fail closed: an error or timeout after the input was read denies the covered call and logs the failure, an absent `profile.json` runs log-only, a malformed `profile.json` (or a bad value under one of their keys) while the profile is enforced denies every covered call until it is fixed, and `ls`, reads, and other calls pass. Known limits: a paraphrase of the data escapes a pattern, each call is judged alone with no session memory, and the FERPA guard cannot tell whether the declared party is the real destination. Each self-test runs a fixed corpus against a temporary project; a false deny disables the guard, and a missed deny keeps it enabled with weak protection. The keys and the decision order are under "Outbound data guards" in `rules/assist-plugin-rule.md`. The `goal-guard` hook runs on `PostToolUse` for `WebFetch`, `WebSearch`, and `mcp__*` results and is advisory only: it applies a fixed, rule-based check (`hooks/lib/hijack-rules.js`, no model and no network call) for text that tries to redirect the agent from the user's goal, such as an order to ignore earlier instructions or to send repository files to a URL. On a match it appends one `goal-guard` record with the decision `would-deny` to the audit log (the event, the decision, the mode `advisory`, a fixed rule id and family, a rule count, the tool name, and the agent identity); when no rule matches it appends one with the decision `pass` (the same fields without a rule id, family, or count). A tool or event outside `WebFetch`, `WebSearch`, and `mcp__*` `PostToolUse` leaves no record. The hook withholds, rewrites, and prints nothing, so the result reaches the agent unchanged. A record never holds the result text, a URL, a query, a path, or a secret. The check is a heuristic signal, not a boundary, and promotion to blocking is a later step. Its self-test uses a stub sink and checks three hijack samples (each must record a would-deny), five clean samples (each must record a pass and no rule id), and three out-of-scope samples (none may record). A failed self-test is reported and never disables the hook, so a false finding means weak detection and the hook stays enabled. The two FSA hooks enforce and check the agent state machines. The `fsa-write-bar` guard keeps `developer-tester` to test paths and keeps `developer` out of them (the globs are under "Write scope" in `agents/developer-tester.md`), limits `task-planner` to `docs/task-plans/task-plan-*.md` under the session's git root, bars `developer-tester`, `task-planner`, `requirements-gatherer`, and `solutions-architect` from dot paths, `CLAUDE.md`, `CLAUDE.local.md`, and `AGENTS.md`, and denies every subagent `.agent/main-plan/**` and `DECISIONS.md`. It also judges a `Bash` call from a subagent: the call is denied when the command writes a protected path (`.agent/main-plan/**`, `DECISIONS.md`, `.agent/logs/governance/**`, the confirmation store) through output redirection (`>`, `>>`, `>|`, `N>`), `tee`, `sed -i`, `cp`, `mv`, `rm`, or a like command, including through a glob, a quoted spelling, a relative path after `cd`, or a `bash -c` string. Reading a protected path (`cat DECISIONS.md`) and writing any other path stay allowed, and the main session is not judged on this route. If the bar fails after its input was read (an error, or a timeout), it denies a subagent `Bash` command that names a protected path and logs the failure; any other call proceeds with a warning. Its known limits: a command built from a variable, a command string run by another program (`python -c`, `node -e`, `find -exec`, `xargs` fed from a pipe), symlinks, a removal of a directory above a protected path named only as `.` or a variable, and PowerShell write verbs (`Set-Content`, `Out-File`, `Move-Item`), which the bar does not see. The `fsa-log` hook runs on `SubagentStop`, on the `SubagentHandback` tool, and on `Agent` results: it parses the last `fsa` terminal block of each report from `developer-tester`, `reviewer`, `code-reviewer`, `developer`, `qa`, `intake-reviewer`, and `task-planner`, checks it against the agent's transition table, and appends one chained row to `${CLAUDE_PLUGIN_DATA}/fsa-log.jsonl`. The file has no line cap: it rotates by size through the audit-chain library, each new segment starts with the prior segment's final chain hash, and segments are kept at least 12 months. It runs in warn mode: a report with problems shows a one-line notice to the user and is never blocked or sent back. Its self-test runs a fixed set of clean and broken reports; a miss in either direction disables it like the filter. This skill shows those records.

## Verify the audit chain

`/assist-plugin:health --verify-audit` runs the third command above. It skips the self-tests, reads the governance audit log, and changes no file. The command calls `scripts/verify-audit-chain.js`, which walks every segment of `.agent/logs/governance/` in order (the rotated `audit-NNNNNN.jsonl` files, then `audit.jsonl`) and follows the chain across each cut. The same check runs from a shell as `node plugins/assist-plugin/scripts/verify-audit-chain.js [root]`.

| Exit | Output | Tell the user |
|---|---|---|
| 0, intact | `Audit chain intact: N lines verified across S segments.` followed by the limit below | The verified line count and the segment count, then the limit |
| 0, empty | `Audit chain: no lines to verify (0 lines in .agent/logs/governance/audit.jsonl).` | The log is missing or empty, so there is nothing to verify |
| 1, broken | `Audit chain BROKEN at line N (segment NAME, line M of that segment). K lines verified before the break.` and a `Reason:` line | The first broken line, its segment, and the reason, and that the log was changed after it was written |
| 2, cannot verify | `Cannot verify the audit chain: ...` on stderr | The project root is unknown or a segment could not be read; the message names the error code |

Line numbers count from 1 across all segments. For a `prev-mismatch` reason, the named line is the last line the chain still confirms: the next line no longer holds its hash, so that line or the next was edited, or a line was removed or reordered after it. An edit to line 7 reports line 7. Any `unidentified` record is counted on an extra line (the flag matches nothing until the per-agent identity step lands).

The limit to repeat when the chain is intact: the chain runs backward, so a line is confirmed only by the line after it. The final retained line and any lines removed from the end of the log are not confirmed by the chain alone; a head anchor outside the log would confirm both, and none is kept yet. State this beside the count and never present the final line as verified.

## Export control evidence

`/assist-plugin:health --export-evidence --from YYYY-MM-DD --to YYYY-MM-DD` runs the fourth command above. It skips the self-tests, reads the governance audit log and `fsa-log.jsonl`, and changes no file. The command calls `scripts/export-control-evidence.js`, which counts and lists the control events in the range (UTC, both dates included) by type: denies, asks, gate evidence, approvals (records that cite a plan approval), disclosures, and logged disablements. It reads every retained segment of both logs (rotated segments are kept at least 12 months) and verifies the chain across each cut, as `--verify-audit` does. The same export runs from a shell as `node plugins/assist-plugin/scripts/export-control-evidence.js --from YYYY-MM-DD --to YYYY-MM-DD [--root DIR] [--data-dir DIR]`.

| Exit | Output | Tell the user |
|---|---|---|
| 0, verified | `Chain verification: VERIFIED for this range.`, then the counts and the listed events by type | The range, the chain result, and the count for each type, with the head-anchor limit the report states |
| 1, unverified | `Chain verification: UNVERIFIED.` and a `... chain BROKEN at line N (segment NAME, line M of that segment)` line with a `Reason:` line | The range is unverified and its counts are not confirmed; the first bad line, its segment, and the reason; that the log was changed after it was written |
| 2, cannot export | `Cannot export control evidence: ...` on stderr | The range was missing or not a real date, the project root is unknown, or a segment could not be read; ask for the dates again or name the error code |

State the source with every export: the evidence comes from the plugin's own hooks and is not a vendor SOC 2 report. The report holds event types, counts, times, segment names and line numbers, and short identifiers (a rule id, a tool name, an agent type, a gate kind, a plan approval reference, a receiving party and its interest label). It holds no prompt text, command text, file contents, path, or secret; never add any. A break after the end of the range leaves the range verified, and the report says so. A break at or before the end of the range marks the range unverified. For a `prev-mismatch` reason the named line is the last line the chain still confirms, as in "Verify the audit chain". Never edit, repair, or truncate a log; report the break.

## Findings and fixes

| Finding | Meaning | Fix |
|---|---|---|
| `unsupported-node` | Node is older than the minimum shown in the message, so guards pass every command unchecked | Install or upgrade Node to the minimum version or newer, then run `/assist-plugin:health` again |
| `node: command not found` (hook error notice) | Node is missing, so guards cannot run and commands proceed unchecked | Install Node (see the Node row in README.md), then run `/assist-plugin:health` again |
| Guard self-test FAIL, "known-safe command was DENIED" | The guard has a bug; it was auto-disabled and passes commands with a warning | Report the bug (include the report output) at https://github.com/tjmonsi/assist-marketplace-plugin/issues. After a plugin update, run `/assist-plugin:health` again; a passing self-test re-enables the guard |
| Guard self-test FAIL, "known-prohibited command was ALLOWED" | The guard misses a case it should block; it stays enabled but protection is weak | Report the bug with the report output |
| Guard self-test FAIL, "case threw" | The guard raised an error on a fixed case | Report the bug with the report output |
| `prose-gate` self-test FAIL, "known-safe write was DENIED" | The gate has a bug; it was auto-disabled and writes pass with a warning | Report the bug (include the report output). A passing self-test after a plugin update re-enables it |
| `prose-gate` self-test FAIL, "known tell was ALLOWED" | The gate misses a tell it should block; it stays enabled but protection is weak | Report the bug with the report output |
| `prose-advisor` self-test FAIL, "clean sample was ADVISED" or "advisory sample was MISSED" | The advisor is unreliable; it was auto-disabled and writes get no advice | Report the bug with the report output. A passing self-test after a plugin update re-enables it |
| `injection-filter` self-test FAIL, "benign sample was ALTERED" or "injection sample was MISSED" | The filter is unreliable; it was auto-disabled and tool results pass through unfiltered with a one-time warning | Report the bug (include the report output; it lists sample labels, not sample text). A passing self-test after a plugin update re-enables it |
| `fsa-write-bar` self-test FAIL, "known-safe write was DENIED" | The write bar has a bug; it was auto-disabled and no agent write limit applies | Report the bug (include the report output). A passing self-test after a plugin update re-enables it |

### FSA problem codes

`fsa-log` stores these short codes in `problems`. Each is checked against the agent's table in `hooks/lib/fsa-tables.js`.

| Code | Meaning |
|---|---|
| `no-block` | The final report has no complete `fsa` block |
| `fsa-mismatch` | The `fsa:` line is not `<agent>/<version>` for this agent (for example `task-planner/1` from `task-planner`) |
| `bad-state` | `state` is not `Done`, `NeedsInput`, or `Error` |
| `missing-field` | A required field (`trace`) is absent |
| `trace-too-long` | `trace` has more than 40 states |
| `unknown-state` | `trace` names a state that is not in the table |
| `bad-start` | `trace` does not begin at `Intake` |
| `illegal-transition: A>B` | The table has no edge from A to B |
| `trace-not-terminal` | `trace` does not end in `Done`, `NeedsInput`, or `Error` |
| `terminal-mismatch` | `trace` ends in a different terminal state than `state` |
| `bad-error-class` | `error_class` is outside the closed list, `none` on an `Error`, or set on a state other than `Error` |
| `bad-verdict` | `verdict` does not match the agent's pattern, or is `none` on a `Done` |
| `bad-resume-at` | A `NeedsInput` has no `resume_at` naming a state of the table |

After fixing a cause, run `/assist-plugin:health` again to confirm; a clean report prints `PASS` for every hook listed and `Disabled guards: none`. Run `/assist-plugin:health --clear` once the log entries have been handled.

## Privacy

The health log holds only timestamp, hook name, Node version, failure kind, and a short message. It never holds command text, arguments, environment values, or hook input.

`fsa-log.jsonl` holds, per report (one chained row, with the hash of the row before it): timestamp, session id, event, agent type, agent id (the agent identity), the human authorizer, and the block fields `fsa`, `state`, `verdict`, `error_class`, `out_of_scope_count` (a count), and `trace`, each copied only when it matches a closed list or pattern (anything else is stored as `<invalid>`), plus the problem codes. The authorizer is a reference to the plan approval the user made (the plan's "Approved" decision, as `plan-approval:<plan file>@<minute>`, or an approval message id), or `none` with a reason (`authorizer_reason`) for an autonomous action or one with no approved plan; it is never omitted and never holds message text. A row holds no operation and no data-accessed field: one report names no single operation or path, so those stay in `audit.jsonl`. The file rotates by size (an estimated 1 MiB until measured), carries the prior segment's final chain hash into each new segment, and keeps segments at least 12 months. It never holds prompts, report text, artifact paths, questions, or file contents.

`.agent/logs/governance/audit.jsonl` holds, per line: the timestamp, the hash of the previous line, the event, and the structured fields of the record: rule id, decision, tool name, a path with its data-class tag, and the agent identity. An access event that carries an `operation` field holds all five attribution fields: the operation, the data accessed (the path and a data-class tag only), the agent identity, the human authorizer (a reference to the plan approval, or `none` with a reason; never omitted and never message text), and the timestamp. It never holds prompts, command text, file contents, tool results, or secret values (NFR-031). A record that carries one is refused and not written; the refusal is noted in `hook-health.jsonl` by field name only. A `guard-disabled` event holds the guard name alone, a `profile-disabled` event holds the profile name alone (`soc2`, `hipaa`, or `ferpa`), and an `audit-initialized` event (written when the first session creates the log) holds no field beyond the event name.

`health-state.json` holds, for the disablement dedup, the guard name, the disable timestamp of its `hooks-disabled.json` entry, and a short truncated hash of each project root already logged. For the profile opt-out dedup it holds, per truncated project-root hash, the names of the profiles already logged. It never holds a path, a cwd, a reason, or a record value.
