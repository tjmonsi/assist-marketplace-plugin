# Commit

Create conventional commits using the Conventional Commits format.

## Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Types:**
- `feat` — A new feature
- `fix` — A bug fix
- `refactor` — Code change without feature/fix
- `docs` — Documentation changes
- `test` — Test changes
- `chore` — Maintenance, dependencies
- `perf` — Performance improvements
- `ci` — CI/CD changes

**Scope (optional):** Component or module affected

**Subject:** Imperative, present tense, no period (50 chars max)

## Examples

```
feat(auth): implement JWT-based authentication

fix(api): resolve null pointer in user endpoint

refactor(database): consolidate query builders

docs(readme): add installation instructions
```

### No Co-Authorship

Commit messages contain no LLM attribution — no footer, no `Co-Authored-By` line.

Correct:
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.
```

Wrong (never do this):
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.

Co-Authored-By: Claude <noreply@anthropic.com>
```

## Options

- `--squash` — Squash commits before committing (clean history)
- `--amend` — Amend the last commit instead of creating new one
- `--scope SCOPE` — Specify scope for the commit

## Workflow

1. Stage your changes: `git add .`
2. Run `/commit`
3. Choose commit type and scope (if prompted)
4. Write commit message
5. Confirm and commit

## Constraints

- Always use Conventional Commits format
- Never commit without review (changes should be reviewed first)
- Keep messages concise and meaningful
- Link to issues/tickets in footer if applicable
- **Commit messages must NOT include co-authorship lines.** No `Co-Authored-By: Claude`, `Generated by Claude`, or any similar LLM attribution, in the subject, body, or footer.
- Do not set `git config user.name`/`user.email` to a Claude or LLM identity. Commits use the local developer's own git identity (`git config user.name`, `git config user.email`), never an assistant name.

## Model

This skill always runs on **Haiku**, the cheapest model tier. Composing a conventional commit message is mechanical (read staged diff, pick a type/scope, write a one-line subject) and needs no deep reasoning. ## Stripping Co-Authorship

No helper script exists for this skill (Bash is the only tool it uses). Enforcement is a hard rule for whoever/whatever composes the message:

1. Never generate a `Co-Authored-By`, `Generated-By`, or `Assisted-By` line for any LLM.
2. If a commit message is drafted with one of these lines (e.g., pasted from another tool), strip it before running `git commit`.
3. Verify with `git log -1 --format=%B` after committing — the output must not mention Claude or any assistant name.

Example strip, if a draft message ever contains one:

```bash
# Remove any Co-Authored-By/Generated-By lines mentioning an LLM before committing
git commit -m "$(printf '%s\n' "$MESSAGE" | grep -v -iE '^(co-authored-by|generated-by|assisted-by):.*claude')"
```

## Report Writing Standard

- Lead with the most important finding; never write "this is the more important of the two."
- Every finding has three parts: what happened, why it matters, what to do next.
- State each conclusion once. One optional summary line at the end for multi-finding reports; never repeat findings there.
- Use active voice, important subject before the verb ("Validation is skipped" not "The validation was skipped by...").
- Cut hedges ("it should be noted," "arguably") and contrastive filler ("This is X, not Y" — state what it is).
- No meta-headers about the act of writing ("What follows," "Key takeaway," "In conclusion").
- No em-dashes; use a period, comma, parentheses, or semicolon.
- No severity badges, remediation blocks, or summary sections unless the reader would be lost without them.
- Never restate the user's prompt or an assumption as fact; report the tested result.
- The first sentence of every paragraph must add new information.
- Applies to commit body prose only; commit subject lines and Conventional Commits type/scope syntax are unaffected.
