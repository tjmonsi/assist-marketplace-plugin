# Commit

Create conventional commits using the Conventional Commits format.

## Format

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Types:**
- `feat`: A new feature
- `fix`: A bug fix
- `refactor`: Code change without feature/fix
- `docs`: Documentation changes
- `test`: Test changes
- `chore`: Maintenance, dependencies
- `perf`: Performance improvements
- `ci`: CI/CD changes

**Scope (optional):** Component or module affected

**Subject:** Imperative, present tense, no period (50 chars max)

## Examples

```
feat(auth): implement JWT-based authentication

fix(api): resolve null pointer in user endpoint

refactor(database): consolidate query builders

docs(readme): add installation instructions
```

### No AI Attribution

Commit messages contain no AI attribution: no AI attribution footer, no `Co-Authored-By` line for an AI tool, no "Generated with" line, no `*-Session:` trailer (such as `Claude-Session:`), and no bare AI session link. Human co-authors are fine. The `commit-attribution-guard` hook denies a `git commit` or `git merge` whose message holds such a line, and lists up to 5 lines to remove. The hook cannot see a message built from a variable or piped through stdin, so the rule still applies when you compose the message.

Correct:
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.
```

Wrong (never do this):
```
feat(auth): implement JWT-based authentication

Add JWT middleware and refresh-token rotation for the login flow.

Co-Authored-By: Claude <noreply@anthropic.com>
```

## Options

- `--squash`: Squash commits before committing (clean history)
- `--amend`: Amend the last commit instead of creating new one
- `--scope SCOPE`: Specify scope for the commit

## Workflow

1. Stage your changes: `git add .`
2. Run `/commit`
3. Choose commit type and scope (if prompted)
4. Write commit message
5. Confirm and commit

## Constraints

- Always use Conventional Commits format
- Never commit without review (changes should be reviewed first)
- Keep messages concise and meaningful
- The Report Writing Standard below applies to the commit body only; the subject line and the Conventional Commits type and scope syntax follow the Format section
- Link to issues/tickets in footer if applicable
- **Commit messages must NOT include AI attribution lines.** No `Co-Authored-By: Claude`, `Generated by Claude`, or any similar LLM attribution, in the subject, body, or footer. Human co-authors and issue links are fine.
- Do not set `git config user.name`/`user.email` to a Claude or LLM identity. Commits use the local developer's own git identity (`git config user.name`, `git config user.email`), never an assistant name. Also never pass an identity through `--author` or `-c user.name=` / `-c user.email=`; a drafted command that carries one drops the override and commits with the developer's own identity.

## Removing AI Attribution

No helper script exists for this skill (Bash is the only tool it uses). Enforcement is a hard rule for whoever/whatever composes the message:

1. Never generate a `Co-Authored-By`, `Generated-By`, or `Assisted-By` line for any LLM, a `*-Session:` trailer (such as `Claude-Session:`), or a bare AI session link.
2. If a commit message is drafted with one of these lines (e.g., pasted from another tool), strip it before running `git commit`.
3. Verify with `git log -1 --format=%B` after committing; the output must hold no AI attribution line of the kinds listed above; if one is there, amend to remove only that line.
4. If the hook denies a command, remove the listed lines from the message. Retry with the same command form. Do not move the message into a variable, a pipe, a file the hook cannot read, or a code fence, and do not edit hooks-disabled.json. If a listed line names a person the user asked to credit, stop and tell the user instead of removing it.

When `attribution.commit` is unset or not `""`, Claude Code's instructions ask you to end the commit message with a Co-Authored-By trailer or a session link. Leave those lines out even then; the commit-attribution-guard denies them. If your instructions asked for such a line, tell the user once that `/assist-plugin:health` reports this setting and that `{"attribution": {"commit": "", "pr": ""}}` in their Claude Code settings turns it off. Never edit a settings file yourself.

## Report Writing Standard

- Put the answer or the most important finding first. No preamble, no restating the question, no closing recap.
- Let content set the length. Report a clean check in one line.
- Give each finding three parts: what happened, why it matters, what to do next.
- State each conclusion once. Open every paragraph with new information.
- Use active voice; put the important subject before the verb.
- Use plain words ("use" for "utilize"). Cut hedges, intensifiers, throat-clearing, buzzwords, and "not X but Y" framing; state what it is.
- Name headings after their content. Skip summary labels ("In conclusion", "Key takeaways"), severity badges, and summary sections unless the reader needs them.
- Write no em dashes (use a period, comma, colon, parentheses, or semicolon), no curly quotes, and no chatbot sign-offs or offers.
- Back every claim with evidence (file and line, log, test result, URL) and every number with a source; label estimates as estimates.
- Report tested results; never present the prompt or an assumption as fact.
- Quote exactly; never reword a quotation.
- Keep ticket ids and internal blame out of user-facing text.
